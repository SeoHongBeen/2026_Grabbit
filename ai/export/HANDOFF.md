# RPi 팀 전달 문서

AI 파트에서 넘기는 것과, RPi 쪽에서 해야 할 일을 정리했습니다.

---

## 1. 넘기는 파일

`export/` 폴더에서 **아래 4개** (총 27MB).

| 파일 | 크기 | 무엇 |
|---|---|---|
| `grabbit.py` | 7KB | 추론 코드 |
| `run_rpi.py` | 13KB | 실시간 실행 (분류 + 방향 + 전송) |
| `grabbit_model.npz` | 11MB | 분류기 가중치 + 임계값 + 전처리 설정 |
| `yamnet.tflite` | 16MB | 특징 추출기 (구글 YAMNet) |

방향 추정을 쓰면 `rpi/` 의 **2개** 를 더 가져갑니다.

| 파일 | 크기 | 무엇 |
|---|---|---|
| `doa_knn_model_v5.pkl` | 18KB | 주하 v5 KNN |
| `doa_scaler.pkl` | 1KB | StandardScaler |

`export_model.py` 는 PC에서 모델을 내보낼 때 쓰는 도구라 안 보내도 됩니다.

**PyTorch·TensorFlow 불필요**합니다. numpy + tflite-runtime 만 있으면 됩니다.

pkl 두 개는 **저장소 배치(`<repo>/rpi/`)를 그대로 유지**해 주세요.
`run_rpi.py` 가 자기 위치를 기준으로 `../../rpi/` 에서 찾습니다. 다른 곳에 두면
방향 추정이 꺼지고 `direction` 이 늘 `-1` 로 나갑니다.

### yamnet.tflite 는 저장소에 없습니다

16MB라 git에 넣지 않았습니다. 파일 전달(드라이브·USB)로 받거나,
아래 명령으로 직접 받으세요. 구글이 배포하는 원본 그대로라 어느 쪽이든 같습니다.

```bash
curl -L -o yam.tar.gz \
  'https://www.kaggle.com/api/v1/models/google/yamnet/tfLite/tflite/1/download'
tar xzf yam.tar.gz && mv 1.tflite yamnet.tflite
```

받은 파일을 `grabbit.py` 와 **같은 폴더**에 두면 됩니다.

**반드시 16MB 버전이어야 합니다.** MediaPipe판(4MB)은 클래스 점수 521개만 내놓고
우리가 쓰는 1024차원 임베딩이 없어서, 실행하면 바로 오류가 납니다.

---

## 2. 설치

```bash
pip install numpy tflite-runtime
sudo apt install alsa-utils

# 방향 추정을 쓸 때만
pip install joblib scipy "scikit-learn==1.6.1"
```

`tflite-runtime` 이 안 깔리면 `pip install tensorflow` 로도 되지만 훨씬 무겁습니다.

**scikit-learn 버전을 맞춰 주세요.** pkl 은 1.6.1 에서 만들어졌습니다.
다른 버전에서 풀면 sklearn 이 경고만 내고 그냥 로드해서, 방향이 조용히
틀릴 수 있습니다.

---

## 3. 실행

```bash
arecord -l                                          # 마이크 확인
python3 run_rpi.py --device plughw:0,0 --channels 4 --host 192.168.137.42
```

`--channels` 는 마이크 채널 수입니다. 테스트에 쓴 마이크 어레이가 4채널이라
그 값을 넣었습니다. 일반 USB 마이크면 `1` 이고, 그때는 방향 추정이 꺼집니다.

`--host` 는 **알림을 받을 폰의 IP** 입니다 (핫스팟 주소). 폰 앱을 아직 안 띄웠으면
`--no-send` 로 전송 없이 마이크·모델만 점검할 수 있습니다.

**`--verbose` 를 붙이면** 판정마다 클래스와 확신도가 출력되어,
소리를 내면서 반응을 눈으로 확인할 수 있습니다.

## 4. 알림 전송 — 이미 구현되어 있습니다

`on_alert()` 안이 채워져 있습니다. `docs/json-schema.md` 스키마 그대로 폰에 POST 합니다.

```
POST http://<폰IP>:8080/alert     Content-Type: application/json
{"class": "siren", "direction": 90, "danger": 3, "timestamp": 1752894000}
```

**이 함수는 "울려야 할 때"만 호출됩니다.** 임계값·연속 조건·쿨다운 판정은
이미 안에서 끝난 상태입니다. RPi 쪽에서 다시 필터링할 필요 없습니다.

- 같은 소리가 계속 나도 쿨다운(`--cooldown`, 기본 10초) 안에는 한 번만 호출됩니다
- 쿨다운 중에도 판정 기록은 계속 쌓이므로, 사이렌처럼 소리가 이어지면
  쿨다운이 풀리는 즉시 다시 울립니다

전송은 **별도 스레드**에서 합니다. 전송이 블로킹되면 그 사이 오디오가 밀리기
때문입니다. 네트워크가 죽어도 감지는 멈추지 않고, 실패는 세기만 해서
종료할 때 성공/실패 횟수를 출력합니다.

### `direction` — 주하 v5 모델이 붙었습니다

4채널 어레이 + pkl 두 개가 있으면 실제 각도가 나갑니다
(`front 0 / right 90 / rear 180 / left 270`). 조건이 안 맞으면 `-1`(unknown)
입니다 — 폰은 `-1` 을 unknown 으로 처리합니다.

계산은 **알림 직전 `--hop` 구간(기본 1초)의 4채널 원본**으로 합니다.
채널 0-2, 1-3 의 상관 지연 두 개와 채널별 RMS 비율 네 개, 총 6차원을
StandardScaler 에 통과시켜 KNN 이 `front/right/rear/left` 를 냅니다.

`-1` 이 나가는 경우는 이렇습니다.

- `--channels` 가 4가 아님
- pkl 을 못 찾음 / sklearn 버전 문제로 로드 실패 (시작할 때 이유가 출력됩니다)
- 그 구간의 최대 음량이 3000(int16) 미만
- 모델이 `front/right/rear/left` 밖의 라벨을 내놓음

`danger` 는 `run_rpi.py` 상단 `DANGER` 표에서 붙입니다 — 스키마 확정 목록과 같은 값입니다.

### 앱 파트에 남은 일: `doorbell` 매핑

`docs/json-schema.md` 를 모델 기준(4종)으로 개정했습니다 — `doorbell` 추가,
`crackling_fire`·`door_wood_creaks` 제거 (2026-08-11).

RPi 쪽은 그대로 두면 됩니다. 다만 폰의 `AlertSpec.kt` `alertMap` 에 `doorbell`
항목이 아직 없어서, 지금 상태로는 **초인종이 POST 는 되지만 워치로 안 넘어갑니다**
(미등록 클래스는 이력만 남기고 스킵). 앱 파트에 반영 요청해 둔 상태입니다.

## 5. 알아둘 동작

### 판정 주기 — `--hop` 을 함부로 바꾸지 마세요

기본 **1초**마다 최근 5초를 듣고 판정합니다.

이 값은 취향이 아니라 **임계값·연속 조건을 정할 때 쓴 값**입니다
(`training/deploy_config.py` 의 `DEPLOY_HOP`). "연속 N회"는 결국
"N × hop 초 동안 지속"이라는 뜻이라, hop 을 바꾸면 요구 지속시간이 통째로
바뀝니다.

**알림이 늦다고 hop 을 줄이지 마세요.** 0.48초로 좁혀봤지만 RPi4가 따라오지
못해 오디오가 밀렸습니다. 대신 연속 조건을 줄이는 쪽으로 해결했고,
실환경 2시간 녹음으로 재보니 손해가 없었습니다.

| 연속 조건 | siren 지연 | knock 지연 | 임계값 | 전체 recall |
|---|---|---|---|---|
| 예전 (siren 4, knock 2) | 4.0초 | 2.0초 | 0.30 | 0.874 |
| **현행 (siren 2, knock 1)** | **2.0초** | **1.0초** | 0.30 | **0.874** |
| 전부 1회까지 | 2.0초 | 1.0초 | glass 0.70 | 0.845 |

사이렌은 오래 울리므로 4회를 요구할 이유가 없었습니다. 반대로 유리·초인종을
1회로 줄이면 임계값이 올라가 `glass_breaking` recall 이 0.96 → 0.88 로
떨어져서 2회를 유지했습니다.

### 연속 조건 — "최근 N+1창 중 N창"

같은 소리가 여러 창에서 나와야 알림이 울립니다. **한 창이 튀어도 처음부터 다시
세지는 않습니다** — 최근 `연속+1` 창을 보고 그중 `연속` 창이 임계값을 넘으면
울립니다.

| 클래스 | 임계값 | 연속 | 보는 창 | 최소 지속시간 (hop 1초) |
|---|---|---|---|---|
| `glass_breaking` | 0.30 | 2회 | 최근 3창 | 2.0초 |
| `siren` | 0.30 | 2회 | 최근 3창 | 2.0초 |
| `door_wood_knock` | 0.545 | 1회 | 최근 2창 | 1.0초 |
| `doorbell` | 0.30 | 2회 | 최근 3창 | 2.0초 |

중간에 한 창을 놓치면 그만큼(1초) 늦어집니다.

유리·노크·초인종은 1~2초짜리라 조건을 높이면 아예 안 울립니다.
이 값들은 실환경 녹음 2시간을 분석해 정한 것입니다.

**체감 지연 = 최소 지속시간 + 처리 시간.** 노크 약 1.5초,
유리 깨짐과 사이렌 약 2.5초로 예상합니다.

### 임계값은 클래스 확률에 직접 걸립니다

argmax(1등)는 보지 않습니다. others 가 1등이어도 그 클래스의 확률이 임계값을
넘으면 한 표로 셉니다. siren 0.45 / others 0.50 이면 siren 을 한 표로 칩니다.

유리 깨짐처럼 others 와 확률을 나눠 갖는 소리가 1등을 못 잡아 몇 초씩 늦어지던
것을 없애기 위한 규칙입니다. `--verbose` 출력의 대괄호 안 값(클래스별 확률)이
실제로 임계값과 비교되는 값이고, 왼쪽의 1등 확률은 참고용입니다.

### 설정 변경

임계값이나 연속 조건을 바꾸고 싶으면 **RPi 코드가 아니라 AI 파트에 요청**하세요.
`grabbit_model.npz` 안에 들어 있고, PC에서 다시 내보내야 합니다.

코드에 직접 적으면 학습·평가·배포가 서로 다른 값을 쓰게 되고,
그 사실은 성능이 무너질 때까지 드러나지 않습니다.

## 6. 성능

**실환경 2시간 녹음 기준** (RPi 마이크로 직접 녹음한 것)

| 클래스 | recall | precision |
|---|---|---|
| `glass_breaking` | 0.96 | 0.91 |
| `siren` | 0.90 | 0.77 |
| `door_wood_knock` | 0.89 | 0.88 |
| `doorbell` | 0.74 | 0.91 |

오알림 **하루 1회 이하** (클래스별 예산 1회/일로 임계값을 잡았습니다).

**주의 두 가지:**

1. **recall은 데이터셋(깨끗한 녹음) 기준입니다.** 마이크에서 5m 떨어진 소리는
   이보다 낮을 수 있으며 아직 측정하지 않았습니다.
2. **오알림 빈도는 2시간 관측 결과입니다.** 통계적으로 하루 몇 회인지
   확정하려면 더 긴 녹음이 필요합니다.

## 7. RPi 팀에 부탁하는 것

### (1) 추론 속도 측정 — 우선, 그리고 전보다 중요해졌습니다

```bash
python3 bench_latency.py      # record/ 폴더에 있음
```

hop 이 1초라 **한 창 처리가 1000ms 안에 끝나야** 합니다. PC에서 31~42ms
나왔지만 **RPi4 실측이 아직 없습니다.** 0.48초로 좁혔을 때 밀린 것으로 보아
480ms는 넘습니다.

`run_rpi.py` 는 종료할 때(Ctrl+C) 추론 시간의 평균과 최대를 출력합니다.
그 숫자를 알려주시면 연속 조건과 임계값을 함께 다시 잡겠습니다 —
`--hop` 만 만지면 알림이 조용히 늦어지거나 밀립니다.

### (2) CPU·메모리 사용률

24시간 상시 동작이라 발열·전력도 봐야 합니다.
`top` 이나 `htop` 으로 확인해 주세요.

### (3) 장시간 안정성

몇 시간 돌렸을 때 메모리가 계속 늘거나 arecord가 끊기는지 확인이 필요합니다.
`run_rpi.py` 는 종료 시 "몇 시간 동안 알림 몇 회"를 출력하니 참고하세요.

### (4) 방향 정확도 재측정

**실제 정확도는 이 통합 상태에서 다시 재지 않았습니다.**
`--no-send --verbose` 로 방향별로 소리를 내보면서 맞는지 확인해 주세요.

특히 v5 를 학습시킨 `collect_direction_data.py` 는 4096샘플(0.256초) 청크를
썼는데, 지금은 `--hop` 구간(기본 1초) 전체에서 상관을 잡습니다. 방향이
자주 틀리면 이 차이가 원인일 수 있으니 결과를 알려주세요.

### (5) 마이크 위치

같은 소리라도 마이크 위치에 따라 성능이 크게 달라집니다.
실제 설치할 위치를 정하면 알려주세요 — 그 조건으로 다시 평가하겠습니다.

## 8. 문제가 생기면

| 증상 | 확인 |
|---|---|
| `arecord: command not found` | `sudo apt install alsa-utils` |
| 녹음이 끊김 | `arecord -l` 로 장치 이름 확인 후 `--device` 지정 |
| 아무 알림도 안 울림 | `--verbose` 로 확신도 확인. `alsamixer` 에서 마이크 음량 조정 |
| 헛알림이 너무 잦음 | 어떤 클래스인지 알려주세요. 임계값 조정은 AI 파트에서 합니다 |
| `1024차원 임베딩 출력이 없습니다` | MediaPipe판(4MB)을 받은 경우입니다. 1번 항목의 안내대로 16MB 버전을 다시 받으세요 |
| `[DoA] 모델 로드 실패` | pkl 두 개가 `<repo>/rpi/` 에 있는지, scikit-learn 이 1.6.1 인지 확인 |
| 방향이 늘 `-1` | `--channels 4` 인지, 소리가 충분히 큰지 (3000/int16) 확인 |
| 알림이 늦음 | 종료 시 출력되는 추론 시간을 확인해 주세요. 7-(1) 을 봐주세요 |

**헛알림이나 놓친 소리가 있으면 그때의 오디오를 저장해서 보내주세요.**
그게 모델을 개선하는 가장 확실한 재료입니다.
